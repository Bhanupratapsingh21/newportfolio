In the world of SaaS, "simple" is a dangerous word.

I recently built an admin panel for a multi-tenant platform where each business (tenant) needed to process their own payments, manage subscriptions, and vault customer cards. It sounds straightforward—until you realize you're balancing **PCI compliance**, **data isolation**, and **UX** all at once [web:1].

Here is how we built a production-ready multi-tenant payment system using Cashfree, tokenization, and the Luhn algorithm (and why Luhn almost tricked me).

## The Rabbit Hole: "Can I Validate Cards Without APIs?"

While building the frontend, I wanted instant validation. I thought:

> "Do I really need to hit a payment API just to check if a card is valid?"

That's when I discovered the **Luhn Algorithm** (also called the Mod 10 check).

And for a moment… it felt like a hack [web:1].

Let's take a card: `5555 5555 5555 4444`

## Clean JavaScript Implementation

Here's a production-friendly version that's clean, readable, and performant [web:1]:

<CodeBlock
    marginBottom="16"
    marginTop="8"
    codes={[
      {
        code:
`/**
 * Validates a card number using the Luhn Algorithm.
 * Note: This checks format, not funds or existence.
 */
function luhnCheck(cardNumber) {
  const digits = cardNumber
    .replace(/\\D/g, '')  // Remove non-digits
    .split('')
    .reverse()
    .map(Number);

  let sum = 0;

  for (let i = 0; i < digits.length; i++) {
    let digit = digits[i];

    // Double every second digit
    if (i % 2 === 1) {
      digit *= 2;
      // If > 9, subtract 9 (same as adding digits)
      if (digit > 9) {
        digit -= 9;
      }
    }

    sum += digit;
  }

  return sum % 10 === 0;
}

// Examples
console.log(luhnCheck("5555555555554444")); // true
console.log(luhnCheck("1234567890123456")); // false`,
        language: "javascript",
        label: "Luhn Algorithm Implementation"
      }
    ]}

## Where I Was Wrong (Important Lesson)

For a second, I thought:

> "This means I can validate cards without any payment gateway."

**Nope.**

<Feedback
    icon
    variant="info"
    title="The Reality Check"
    description="Luhn only checks format and structure. It does NOT check: real card existence, CVV correctness, bank approval, or available balance. You can generate fake 'valid' cards all day."
/>

Here's where the "Junior" mindset meets the "Senior" reality [web:1]:

<Row fillWidth gap="8" marginBottom="16" marginTop="8">
  <Column fillWidth border="neutral-alpha-medium" padding="16" radius="m" background="surface-weak">
    <Text variant="label-default-s" onBackground="critical-weak" marginBottom="8">Junior Dev</Text>
    <Text variant="body-default-s">"I'll use Luhn to validate the card so I don't need a payment gateway yet."</Text>
  </Column>
  <Column fillWidth border="neutral-alpha-medium" padding="16" radius="m" background="surface-weak">
    <Text variant="label-default-s" onBackground="success-weak" marginBottom="8">Senior Dev</Text>
    <Text variant="body-default-s">"Luhn is a UI feature, not a security feature."</Text>
  </Column>
</Row>

Luhn checks **syntax**, not **semantics**. A mathematically valid card number could be expired, cancelled, or completely non-existent. It's the difference between checking if a phone number has 10 digits and checking if someone actually picks up the phone.

## Key Takeaways (From a Dev Who Almost Over-Engineered This)

    <Text variant="label-default-s" onBackground="brand-weak" marginBottom="8">1. Luhn ≠ Payment Validation</Text>
